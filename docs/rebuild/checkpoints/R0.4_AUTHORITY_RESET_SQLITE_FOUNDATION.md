## Outcome

R0.4 establishes SQLite as the sole active durable-state authority for the
Linux-local, single-user rebuild. Node 24 `node:sqlite` owns connections and
transactions; the canonical file is `<data-root>/fdbtrade.sqlite3`, with
repository-local `.fdbtrade` as the default and an absolute `FDB_DATA_ROOT`
override.

No command in this work unit inspected, mutated, stopped or deleted the
already-running legacy PostgreSQL state observed during R0.3.

## Authority map

| Concern | R0.4 authority | Evidence |
|---|---|---|
| Data root and connection | `backend/src/db/sqlite.mjs`, `backend/src/db/client.ts` | Absolute override validation, foreign keys, WAL, synchronous `FULL`, bounded busy timeout, `0700` directory and `0600` database. |

| Python configuration mirror | `infra/config/schema.py` | Local data root and busy timeout only; PostgreSQL and Redis namespaces removed. |

Application connections are lazy. A production build does not create or open
durable state during module evaluation. Health checks are read-only and never
initialize a missing database.

## Migration and transaction behavior

- Up migrations are ordered lexically and each migration plus its ledger row
  commits inside one `BEGIN IMMEDIATE` transaction.
- Re-running migrate is a no-op; changing an applied migration produces a hard
  checksum failure.
- A syntactically failing migration rolls back its partial schema and writes no
  ledger row.
- Rollback targets only the latest applied migration and requires its explicit
  down file.
- Tests use temporary files or migrated in-memory databases. There is no
  Docker, network port, credential, operator database or external-state skip.

## PostgreSQL, Redis and Docker retirement

ADR-0037 records the cutover and retirement plan. Active Compose configuration,
network database/cache environment variables, `pg` dependencies and operator
instructions were removed. The old PostgreSQL migrations remain under
`backend/db/migrations` only as historical evidence; the active runner never
reads that directory.

No automatic legacy-data import occurs. Ownership and pre-R0.3 contents of the
legacy database are unknown, old sessions should not cross an authority reset,
and the prior audit store was memory-only. The one local user must be
provisioned explicitly.

The false-success PostgreSQL backup/restore fallback was retired. Both legacy
scripts now exit non-zero and state that no SQLite backup/restore authority has
yet been approved. Backup/restore design and drills remain a later operational
hardening gap.

## Parity evidence

- The real migration CLI creates a clean temporary database, re-migrates
  idempotently, rolls back, reapplies, verifies permissions and passes SQLite
  integrity checks.
- The real provisioning CLI and backend prove unauthenticated denial, uniform
  bad-credential behavior, successful login, HTTP-only cookie issuance,
  authenticated session lookup, survival across backend restart, logout and
  post-logout denial.
- Audit tests close and reopen a file-backed database and recover the identical
  event stream. Direct SQL update and delete attempts fail with the append-only
  trigger error.
- Relative data roots fail closed and a health probe cannot create an absent
  database.
- Backend production build completes without opening a database. The remaining
  Next middleware deprecation notice is unrelated and deferred.
