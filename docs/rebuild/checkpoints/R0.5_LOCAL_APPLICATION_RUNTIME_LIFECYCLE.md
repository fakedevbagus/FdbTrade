## Outcome

R0.5 makes `scripts/fdbtrade` the single bounded lifecycle for the local
frontend and backend. Both Next commands pin loopback explicitly; start
requires migrated SQLite, detects occupied ports even when listener PIDs are
hidden, waits at most 60 seconds for both applications, and tears down its own
partial start. Stop never infers ownership from a port: it requires the
recorded PID and Linux process-start token before signalling that exact process
group.

Scheduler runtime state is no longer production-shaped in-memory state.
Migration `0004_runtime_lifecycle` and `SqliteRuntimeStore` persist locks,
cycle leases, digest-bearing checkpoint chains, completions and cross-domain
dedupe in the canonical database. The PostgreSQL advisory-lock adapter was
removed.

## Lifecycle authority

| Concern | R0.5 authority | Behavior |
|---|---|---|
| Operator entrypoint | `scripts/fdbtrade start/status/stop` | One frontend/backend lifecycle; `make start` delegates here. |
| Network surface | frontend `127.0.0.1:3000`, backend `127.0.0.1:3100` | No public bind and no port fallback. |
| Process ownership | `<data-root>/run/lifecycle.json` | Ephemeral, non-authoritative metadata; PID plus `/proc` start token required. |
| Durable runtime state | SQLite migration 0004 | Locks, leases, checkpoints, completions and dedupe only. |
| Scheduler wiring | backend Node instrumentation | Observation-only and OFF by default; bounded interval required when enabled. |
| Health | `GET /api/health` plus CLI status | SQLite lock, incomplete cycles, last completion and checkpoint integrity. |

The lifecycle JSON does not compete with SQLite: it answers only which OS
process groups this invocation may stop. It is never consulted for scheduler
progress, dedupe, recovery or application health.

## Recovery and transaction behavior

- Lock acquire, heartbeat, release and stale takeover use short
  `BEGIN IMMEDIATE` transactions. A second live owner is rejected.
- Each cycle transition is written to `runtime_cycles`. Checkpoints are
  append-only per cycle and hash stage identity, stage digest and the previous
  link.
- Startup unions checkpointed and leased incomplete cycles, verifies the whole
  chain, and resumes only after the last committed stage. A corrupt chain
  aborts recovery instead of advancing.
- Completion is first-write-wins. Dedupe keys remain first-write-wins across a
  database close/reopen and reject a changed payload for the same key.
- Every tick renews the process lock. A lost lock stops further admission.
- The scheduler remains observation-only and cannot submit paper or live
  orders.

## Truthful health

The public health route distinguishes a deliberately disabled scheduler from
an enabled healthy scheduler. When enabled, a missing/stale lock or corrupt
checkpoint chain degrades overall health. A real backend smoke with a temporary
data root and `FDB_RUNTIME_SCHEDULER=on` reported a held SQLite lock, advanced
durable completions, and removed the lock on SIGINT.

A simultaneous two-app manual smoke was deliberately not forced on this host:
an unrelated wildcard listener already occupied port 3000. The corrected CLI
detected that condition even though `ss` exposed no PID and refused to touch
the listener. Hermetic behavior tests cover the coordinated two-process start,
readiness bound and ownership refusal; the required acceptance authority is
the repository toolchain gate.
